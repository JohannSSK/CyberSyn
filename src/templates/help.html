Quick start
  1. 1 Create an administrator account from the sign-in screen.
  2. 2 Sign in as administrator, then add your team members.
  3. 3 Sign in as the member whose settings you want to configure.
  4. 4 In Settings, select the provider, enter a key and save the model and checks with administrator approval.
  5. 5 Open Statistics as the administrator to see who was blocked, why, and when.
The three checks

Enabled checks run in parallel under one time budget. Blocks are reported in stage order.

1 Personal & Greek IDs

Greek tax numbers and IBANs are checked by checksum; Greek IDs by format and context. Checks also cover AMKA dates, phones, emails, modern API keys and company names.

Local English and Greek name-recognition models check for personal names.

2 Confidential context

Patterns and IBAN/card checksums detect credentials, banking data and strong indicators of confidential records. A local zero-shot model classifies ambiguous text.

Source code is allowed by default. An administrator can switch on code blocking for an individual member in Settings without changing anyone else’s policy.

3 Prompt injection

Instructions trying to override the model's rules, jailbreaks, and payloads hidden inside code comments.

The scanner examines adjacent lines, Python, SQL and JavaScript comments, block and HTML comments, quoted strings and docstrings.

Accounts and roles

Two-step sign-in: the administrator signs in first, then picks which team member to work as.

Administrator Adds and removes members, sets policy, approves overrides, sees statistics and the roster
Team member Their own chats, their own settings. Statistics and the roster are not shown to members

A member's session only ever reads that member's own chats. Opening another member's chat is refused by the server, not merely hidden in the interface.

Member sign-in ends the browser’s administrator session. A single-use approval lasts five minutes. A read-only page unlock lasts fifteen minutes; Lock now revokes it on the server.

What stays local
Your prompts Screened locally; allowed prompts are sent to the selected provider
Your API key Stored encrypted; used to authenticate to the selected provider
Blocked messages Not sent unless a workspace administrator approves an exception
Inspection itself No third-party classifier is consulted
Detected items Matching snippets are returned to the sender for editing, never stored in the block or activity log as block evidence
When a check cannot run

The gate fails closed: if a scanner errors, times out or returns no verdict, the prompt is refused rather than forwarded. You will see an error naming the check instead of a reply.

This is deliberate. A gateway that waves traffic through when it is unwell is worse than no gateway, because it looks like protection while providing none.

What is stored, and how
Chats and messages SQLite, on the server
Provider API keys Encrypted at rest (Fernet), shown masked
Passwords Hashed — never stored in a readable form
Block log Stage and category, with a timestamp
Sessions HttpOnly session cookies; server-side expiry and revocation

Discovery contacts the selected provider. Deleting a chat removes its messages, not audit events. Prompt previews are off by default and never recorded for blocked or overridden sends.

Configuration

Every setting has a default; set an environment variable only when you need to override it.

CYBERSYN_HOST / CYBERSYN_PORT Bind address — default 127.0.0.1:5000
CYBERSYN_DB_FILE Where the SQLite database lives
CYBERSYN_KEY The Fernet key that decrypts stored API keys. Without it, a fresh key is generated and saved
CYBERSYN_AI_TIMEOUT Seconds to wait for the provider — default 60
CYBERSYN_CHECK_TIMEOUT Seconds to wait for a scanner — default 60
CYBERSYN_SCANNER_FALLBACK Fallback can start one subprocess if a scanner cannot be imported. It is off in Docker. A scanner that throws at runtime fails closed.
CYBERSYN_WARM_MODELS Enabled by default. Set to 0 to skip background warm-up.

Troubleshooting

“No usable models” when refreshing models

The key was accepted but no chat-capable model came back. Check the key has access to a chat model on that provider, and that the provider is reachable from the server.

Model discovery names the wrong provider

Automatic discovery uses recognized key prefixes only. Select your provider explicitly for unfamiliar or ambiguous formats; your key is not tried against unrelated services.

Every message is refused

That is the gate failing closed. The check named in the error is the one that could not run — usually a model that failed to load.

The first message is slow

Background warm-up is enabled by default. Set CYBERSYN_WARM_MODELS=0 only if you prefer loading models on first use.

Statistics will not load

Statistics are for administrators. Sign in as the administrator, then open the page.
